Lesson 3 – Classes and Instances
Goal

By the end of this lesson, you should understand:

What is a class?
What is an instance (object)?
Why do classes exist?
Why are almost all ML frameworks built around classes?
Why is AutoModelForCausalLM a class but model is an object?
Let's start with a problem

Imagine you are building a music app.

You need to represent songs.

Without classes, you might write:

song1_name = "Believer"
song1_artist = "Imagine Dragons"
song1_duration = 204

song2_name = "Perfect"
song2_artist = "Ed Sheeran"
song2_duration = 263

Now imagine you have:

10 songs
1,000 songs
1 million songs

You would end up with thousands of unrelated variables.

There is no structure.

The question

Every song has:

Name
Artist
Duration

Every song can:

Play
Pause
Stop

So why repeat this definition for every song?

There must be a better way.

The Solution: A Class

A class is a blueprint.

It describes what every song should have.

Think of it like an architectural drawing.

          House Blueprint

        Rooms
        Doors
        Windows
        Kitchen

The blueprint is not a house.

It only describes how a house should be built.

Python example
class Song:
    pass

Have we created a song?

No.

We have only created a blueprint.

Then what is an object?

When we build a house from the blueprint...

...that real house is called an instance (or object).

Blueprint
     │
     ▼
House 1

Blueprint
     │
     ▼

Blueprint
     │
     ▼

One blueprint.

Many houses.

Translate this to Python
class Song:
    pass

Blueprint.

Now:

song1 = Song()

song2 = Song()

Python creates:

Song Class
      │
      ├────────► song1 Object

      └────────► song2 Object

Notice something.

There is only one class.

But many objects.

Real-world analogy

Think about car manufacturing.

Toyota has a design for a Corolla.

That design is the class.

Every Corolla that rolls off the factory line is an instance.

Corolla Design

        │

────────┼────────

Car 1

Car 2

Car 3

Car 4

Nobody says:

"Toyota creates a new design every time."

The design already exists.

It creates new cars.

Python classes work exactly the same way.

Why is this useful?

Instead of writing:

model1_layers = ...

model2_layers = ...

model3_layers = ...

We define one class.

class Model:
    ...

Now we can create:

model1 = Model()

model2 = Model()

model3 = Model()

Cleaner.

Organized.

Reusable.

Where do methods live?

Consider:

class Dog:

    def bark(self):
        print("Woof")

Question:

Does every object store its own copy of bark()?

No.

There is one method definition on the class.

Each object can use it.

This saves memory and keeps behavior consistent.

We'll understand self in the next lesson.

Why do ML frameworks love classes?

Because they let us define reusable behavior.

Think about a model.

Every model has:

weights
configuration
device
dtype

Every model can:

train
evaluate
generate
save
load

Instead of rewriting those capabilities for every model, we define classes that provide them.

Different model classes can then customize or extend that behavior.

Notes
Topic: Classes and Instances
What is a Class?

A class is a blueprint that defines the data and behavior shared by a type of object.

What is an Instance?

An instance (object) is a real object created from a class.

Why do classes exist?

To avoid repeating the same structure and behavior for every object.

Mental Model

Blueprint → House

Class → Object

Key Ideas
A class is a definition.
An object is a real instance created from that definition.
One class can create many objects.
Objects have their own state.
Objects share behavior defined by the class.
Example
class Dog:
    pass

dog1 = Dog()
dog2 = Dog()

Dog is the class.

dog1 and dog2 are two different objects.

Where will I see this?
torch.nn.Module is a class.
torch.Tensor is a class.
AutoTokenizer is a class.
AutoModelForCausalLM is a class.
Your SDK client classes.
Why does this matter?

Every major Python ML framework is built using classes. Understanding classes lets you reason about how libraries are designed instead of treating them as collections of unrelated functions.

Quick Summary
Class = Blueprint.
Object = Instance.
One class can create many objects.
Objects have their own state.
Behavior is defined by the class and shared by its instances.
