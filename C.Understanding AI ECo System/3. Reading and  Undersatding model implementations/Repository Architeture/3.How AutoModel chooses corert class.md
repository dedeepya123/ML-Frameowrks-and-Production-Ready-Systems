# Module 1 — Lesson 3

# How AutoModel Chooses the Correct Class

## Problem

Users should not need to manually choose:

- Config class
- Model class
- Tokenizer class

A single API should work for many architectures.

---

## Key Metadata

The model repository contains:

config.json

Important field:

model_type

Example:

model_type = "gemma"

---

## Internal Idea

AutoModel reads:

model_type

↓

Looks up implementation in a registry

↓

Instantiates the corresponding class

↓

Loads weights

---

## Conceptual Registry

MODEL_MAPPING

"gemma" → GemmaModel

"llama" → LlamaModel

"bert" → BertModel

---

## Design Pattern

Factory Pattern

AutoModel acts as a factory.

It decides which concrete class to instantiate based on configuration metadata.

---

## Key Takeaways

- AutoModel does not implement model architectures.
- It uses model metadata to select the correct implementation.
- Registries make the system extensible.
- The same dispatch idea is used for Config, Tokenizer, and Processor.

**How does AutoModel know which class to create?**

A good answer is:

Every pretrained model repository includes configuration metadata containing a model_type. Hugging Face uses that value to look up the corresponding implementation class in an internal registry, instantiates the class, and then loads the checkpoint into it. This lets one API support many architectures without hardcoding model-specific logic
