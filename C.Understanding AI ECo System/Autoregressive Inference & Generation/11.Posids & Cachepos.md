# Module 9 — Autoregressive Inference & Generation

## Lesson 13 — `position_ids` and `cache_position`

### 1. Why position information is needed

A token representation alone does not tell the model where that token occurs in the sequence.

Example:

```text
tokens:
[A B C D E]

positions:
[0 1 2 3 4]
```

For RoPE-based models, position information determines the rotary transformation applied to Q/K.

---

### 2. `position_ids`

`position_ids` represent the logical positions associated with the input tokens for positional encoding.

During prefill:

```text
input_ids:
[A B C D E]

position_ids:
[0 1 2 3 4]
```

During decode:

```text
input_ids:
[F]

position_ids:
[5]
```

Next:

```text
input_ids:
[G]

position_ids:
[6]
```

---

### 3. Connection to RoPE

Conceptually:

```text
Q ──┐
    ├── RoPE(position_ids)
K ──┘
```

The position determines the rotary angle/phase used for the corresponding Q/K representation.

---

### 4. Decode example

Suppose the cache already contains positions:

```text
0 1 2 3 4
```

The next token:

```text
F
```

is processed as:

```text
input_ids     = [F]
position_ids  = [5]
cache_position = [5]
```

Then the next token uses position 6.

---

### 5. `cache_position`

`cache_position` tracks the logical sequence positions of the current tokens relative to the KV cache.

It answers:

> Where does this token belong in the cached sequence?

It is especially useful when cache storage is not simply implemented as repeated tensor concatenation.

---

### 6. `position_ids` vs `cache_position`

They are related but represent different concepts.

```text
position_ids
→ positions used by model positional encoding

cache_position
→ logical positions of tokens in the cache
```

For ordinary contiguous autoregressive generation, they often have the same numeric values.

Do not assume they are conceptually identical.

---

### 7. Prefill

For a prompt of length `N`:

```text
position_ids = [0, 1, ..., N-1]
```

The model processes all prompt positions and initializes the KV cache.

---

### 8. Decode

After prefill:

```text
cache length = N
```

Next token:

```text
position = N
```

Then:

```text
position = N+1
position = N+2
...
```

Only the newly generated token needs to be processed because previous K/V states are cached.

---

### 9. Dynamic vs Static cache

Dynamic cache:

```text
cache grows

N → N+1 → N+2
```

Static cache:

```text
fixed capacity

[positions 0 ... N ... max_length]
             ↑
        write current state
```

`cache_position` is particularly useful for identifying where the current state belongs in such a cache.

---

### 10. Where are positions created?

Do not assume `Attention.forward()` creates `position_ids`.

In a real framework they may be:

* passed explicitly,
* created by model input preparation,
* derived from attention/cache state,
* managed by generation/runtime code.

When reading production code, trace them backward:

```text
Attention
 ↑
DecoderLayer
 ↑
Model
 ↑
model input preparation
 ↑
generation loop
```

---

### 11. RoPE and inference

For each logical position, RoPE needs the corresponding positional rotation parameters.

Implementations commonly precompute/cache cosine and sine tables instead of recomputing all values from scratch for every token.

If the required sequence length exceeds the available RoPE range, the implementation may extend/update those tables.

---

### 12. Complete decode flow

```text
generate()
    ↓
prepare inputs
    ├── input_ids
    ├── position_ids
    ├── cache_position
    └── cache
    ↓
model.forward()
    ↓
Q/K/V
    ↓
RoPE(position_ids)
    ↓
rotated Q/K
    ↓
cache.update(...)
    ↓
historical + current K/V
    ↓
attention
    ↓
logits
    ↓
next token
    ↓
repeat
```

### Core takeaway

> `position_ids` tell the model which logical positions to use for positional encoding, while `cache_position` tracks where the current tokens belong in the runtime KV cache. During ordinary generation they often contain the same numbers, but they serve different conceptual responsibilities.
