# Module 9 — Autoregressive Inference & Generation

## Lesson 6 — Prefill vs Decode

### 1. Generation has two phases

```text
Generation
├── Prefill
└── Decode
```

**Prefill:** process the complete prompt and create the initial KV cache.

**Decode:** generate new tokens one at a time while reusing the KV cache.

---

### 2. Prefill

Example:

```text
Prompt = 1000 tokens
```

The Transformer processes the prompt together:

```text
[1000 tokens]
      ↓
Transformer
      ↓
KV cache
      ↓
first generated token
```

Prefill benefits from high parallelism and large matrix operations.

---

### 3. Decode

After the first token:

```text
new token
    ↓
Q_new, K_new, V_new
    ↓
append K_new/V_new to cache
    ↓
Q_new attends to cached K/V
    ↓
next token
```

For a single sequence, only one new position is processed per decoding step.

---

### 4. Why decode still does significant work

Even though only one new position is computed, the new query must interact with the entire cached history:

```text
Q_new × K_cacheᵀ
```

and then use:

```text
attention_weights × V_cache
```

Therefore:

> One new token does not mean one tiny operation. The new token interacts with the full context.

---

### 5. Prefill vs Decode characteristics

| Property         | Prefill                 | Decode                         |
| ---------------- | ----------------------- | ------------------------------ |
| Input            | Whole prompt            | New position                   |
| Parallelism      | High                    | Lower per sequence             |
| KV cache         | Created                 | Read + extended                |
| Workload         | Large matrix operations | Repeated small-step operations |
| Typical pressure | Compute                 | Memory/bandwidth               |
| Latency metric   | TTFT                    | TPOT / inter-token latency     |

"Compute-bound" and "memory-bound" are tendencies, not universal rules.

---

### 6. TTFT

**Time To First Token**

```text
request
  ↓
prefill
  ↓
first generated token
```

Long prompts generally increase TTFT because more prompt processing is required.

---

### 7. TPOT / Inter-token latency

After the first token:

```text
decode
 ↓
token
 ↓
decode
 ↓
token
```

Time per output token or inter-token latency measures how quickly subsequent tokens are generated.

Long generations increase total decoding time.

---

### 8. Why KV cache matters

Without KV cache:

```text
every decode step
→ recompute previous sequence
```

With KV cache:

```text
prefill
→ create KV history

decode
→ compute only new Q/K/V
→ reuse cached history
```

KV cache therefore removes substantial redundant computation.

---

### 9. Generation loop — conceptual view

```python
# Prefill
outputs = model(prompt, use_cache=True)
cache = outputs.past_key_values
next_token = sample(outputs.logits)

# Decode
while not finished:
    outputs = model(
        input_ids=next_token,
        past_key_values=cache,
        use_cache=True,
    )

    cache = outputs.past_key_values
    next_token = sample(outputs.logits)
```

Real implementations additionally handle batching, masks, position IDs, stopping criteria, sampling strategies, and cache implementations.

---

### 10. Core reasoning

```text
Prefill:
many prompt tokens
→ process together
→ high parallelism
→ large computation
→ tends to be compute-heavy

Decode:
one new position
→ interact with growing KV history
→ repeatedly read cached data
→ tends to create memory/bandwidth pressure
```

### Most important takeaway

> **Prefill processes the existing context; decode extends that context one new position at a time using the KV cache. Their workloads are fundamentally different, which is why LLM inference optimization treats them as separate phases.**
