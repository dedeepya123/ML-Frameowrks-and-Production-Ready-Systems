# Module 9 — Autoregressive Inference & Generation

## Lesson 9 — `past_key_values`

### 1. What is `past_key_values`?

`past_key_values` represents the previously computed attention K/V state used during autoregressive generation.

Conceptually:

```text
past_key_values
│
├── Layer 0 → (K₀, V₀)
├── Layer 1 → (K₁, V₁)
├── Layer 2 → (K₂, V₂)
└── ...
```

---

### 2. Why one K/V pair per layer?

Every decoder layer has different:

* hidden representations
* K/V projection weights
* attention computation

Therefore each layer has its own K/V history.

---

### 3. First forward pass

No previous cache:

```text
past_key_values = None
```

The model processes the prompt and computes K/V for all positions.

Conceptually:

```text
prompt
  ↓
Transformer
  ↓
logits + KV state
```

The KV state becomes `past_key_values`.

---

### 4. Subsequent forward pass

The next generation step receives:

```text
new token
+
past_key_values
```

Conceptually:

```text
new token
   ↓
Q_new, K_new, V_new
   ↓
add K_new/V_new to previous K/V
   ↓
attention uses Q_new + complete K/V history
   ↓
updated cache
```

---

### 5. Cache is runtime state

Model weights:

```text
shared across requests
learned during training
```

KV cache:

```text
specific to a request
created during inference
changes every generation step
```

---

### 6. State-passing mental model

Generation behaves conceptually like:

```python
output, state = model(input, state)
```

where:

```text
state = KV cache
```

Then:

```python
output, state = model(next_input, state)
```

The cache is therefore:

> output state of one step and input state of the next.

---

### 7. `use_cache=True`

Conceptually:

```python
use_cache=True
```

means:

> Maintain/return the K/V state required for efficient autoregressive generation.

Caching is primarily an inference optimization.

---

### 8. Historical representation

Older Hugging Face implementations commonly represented the cache conceptually as:

```python
past_key_values = (
    (K0, V0),
    (K1, V1),
    ...
)
```

This is essentially:

```text
layer → (K, V)
```

---

### 9. Why `Cache` abstraction appeared

As inference became more sophisticated, the raw tuple representation became limiting.

Requirements include:

```text
update
reorder
crop
sequence length management
different cache strategies
different memory layouts
generation-specific operations
```

Therefore HF introduced richer cache abstractions.

Conceptually:

```text
raw K/V state
     ↓
past_key_values
     ↓
richer Cache abstraction
```

The underlying concept remains the same:

> cached K/V attention state.

---

### 10. Important API-reading rule

Do not assume:

```python
past_key_values
```

always means a nested tuple.

The variable name describes the concept.

The actual object may be:

```text
tuple
Cache object
another cache implementation
```

depending on the framework/model/version.

Always inspect the actual type and implementation.

---

### 11. Simplified generation loop

```python
past_key_values = None

while not finished:

    outputs = model(
        input_ids=input_ids,
        past_key_values=past_key_values,
        use_cache=True,
    )

    logits = outputs.logits

    past_key_values = outputs.past_key_values

    next_token = select_token(logits)

    input_ids = next_token
```

Reasoning:

```text
First call:
None → create cache

Next call:
previous cache → reuse it

Every call:
new K/V → update cache
```

---

### 12. Core mental model

```text
Forward N
    ↓
produces KV state
    ↓
past_key_values
    ↓
Forward N+1
    ↓
consumes previous state
    ↓
produces updated KV state
    ↓
repeat
```

### Most important takeaway

> `past_key_values` is not a mysterious generation feature. It is the framework-level representation of the persistent K/V attention state that allows successive forward calls to continue autoregressive generation without recomputing historical K/V.
