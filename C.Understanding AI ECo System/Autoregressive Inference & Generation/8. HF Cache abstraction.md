# Module 9 — Autoregressive Inference & Generation

## Lesson 10 — Hugging Face `Cache` Abstraction

### 1. Why `Cache` exists

A simple cache can be represented as:

```python
past_key_values = (
    (K0, V0),
    (K1, V1),
    ...
)
```

This works, but production inference needs behavior such as:

```text
update
retrieve
sequence-length management
reorder
crop
different storage strategies
memory management
```

Therefore a richer abstraction is useful.

---

### 2. Core idea

Instead of exposing the underlying K/V representation directly:

```text
Attention
   ↓
raw tuple structure
```

use:

```text
Attention
   ↓
Cache abstraction
   ↓
actual K/V storage
```

Attention depends on the cache's behavior rather than its internal representation.

---

### 3. Separation of responsibilities

#### Attention

```text
compute Q/K/V
apply RoPE
perform attention
```

#### Cache

```text
maintain K/V history
update K/V
manage cache state
```

#### Generation

```text
run model repeatedly
select next token
stop generation
```

---

### 4. Cache is runtime state

Model weights:

```text
learned
persistent
shared across requests
```

KV cache:

```text
generated at runtime
request-specific
changes every generation step
```

---

### 5. Per-layer state

Conceptually:

```text
Cache
│
├── Layer 0 → K₀/V₀
├── Layer 1 → K₁/V₁
├── Layer 2 → K₂/V₂
└── ...
```

The cache structure mirrors the decoder-layer structure.

---

### 6. Polymorphism

Different cache implementations can provide the same conceptual interface:

```text
                Cache
                  ↑
         ┌────────┴────────┐
         │                 │
   DynamicCache       StaticCache
```

Attention can interact with the abstraction without needing to know the concrete implementation.

---

### 7. Why this matters

The model should not need to know whether the cache:

* dynamically grows
* is statically allocated
* uses a different memory strategy
* supports special windowing behavior
* uses another internal representation

The cache abstraction hides those implementation details.

---

### 8. `update()` concept

Current computation:

```text
K_new
V_new
```

Previous state:

```text
K_cache
V_cache
```

Conceptually:

```text
old K/V + new K/V
        ↓
updated cache
```

The actual implementation does not necessarily perform a naïve `torch.cat()` every step.

---

### 9. Why not expose raw tuples everywhere?

If every component knows:

```text
cache[layer][0] = K
cache[layer][1] = V
```

then the entire framework becomes coupled to one representation.

An abstraction allows the internal representation to evolve without changing every caller.

---

### 10. Runtime architecture

```text
generate()
    ↓
Model
    ↓
DecoderLayer
    ↓
Attention ─────→ Cache
```

The cache is not a neural-network layer.

It is runtime infrastructure supporting efficient autoregressive inference.

---

### 11. Cache is more than storage

Think:

```text
Cache = state + operations + invariants
```

rather than simply:

```text
Cache = container of tensors
```

---

### 12. Evolution

```text
Raw K/V
   ↓
past_key_values
   ↓
Cache abstraction
   ↓
DynamicCache / StaticCache / other implementations
```

The underlying concept remains the same:

> Persistent K/V attention state used across autoregressive decoding steps.

### Core takeaway

> The `Cache` abstraction separates attention computation from the details of how inference-time K/V state is stored, updated, and managed.
