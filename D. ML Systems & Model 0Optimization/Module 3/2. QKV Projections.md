# Module 3 — Transformer Inference Cost
## Lesson 2 — Q/K/V Projections

## 1. Why Q/K/V?

Attention needs three different roles:

- Query: what information am I looking for?
- Key: what information does each token offer for matching?
- Value: what information should actually be retrieved?

The same hidden representation X is transformed into:

    Q = XWQ
    K = XWK
    V = XWV

---

## 2. Input

After embedding:

    X = [B, S, D]

where:

- B = batch size
- S = sequence length
- D = hidden dimension

---

## 3. Q/K/V are Linear transformations

Each projection is a matrix multiplication:

    Q = XWQ
    K = XWK
    V = XWV

Therefore Q/K/V projections are fundamentally different from embedding.

Embedding:

    token ID
        ↓
    lookup

Q/K/V:

    hidden states
        ↓
    matrix multiplication

---

## 4. Typical shapes

For standard MHA:

    X = [B, S, D]

    Q = [B, S, D]
    K = [B, S, D]
    V = [B, S, D]

Then Q/K/V are reshaped into attention heads.

If:

    num_heads = H
    head_dim = d

then:

    D = H × d

and conceptually:

    Q = [B, S, H, d]
    K = [B, S, H, d]
    V = [B, S, H, d]

---

## 5. Q/K/V weights are model parameters

For example:

    WQ = [D, DQ]
    WK = [D, DK]
    WV = [D, DV]

These weights are part of the model and are stored in the checkpoint.

They are different from the runtime KV cache.

### Model parameters

    WQ
    WK
    WV

### Runtime state

    K cache
    V cache

---

## 6. Q/K/V parameter count

For standard MHA where:

    DQ = DK = DV = D

each projection has approximately:

    D × D

parameters.

Together:

    3D²

parameters, ignoring bias.

Example:

    D = 4096

then:

    3 × 4096²
    ≈ 50.3 million parameters

At FP16 this is approximately:

    100.7 MB

of weight storage.

---

## 7. Compute cost

Matrix multiplication:

    [B,S,D] × [D,Dout]

requires approximately:

    2 × B × S × D × Dout

FLOPs.

Therefore:

Q projection:

    ~2BSDDQ

K projection:

    ~2BSDDK

V projection:

    ~2BSDDV

Total:

    ~2BSD(DQ + DK + DV)

For standard MHA:

    ~6BSD²

The exact implementation and FLOP accounting can vary, but this is the
important first-order scaling relationship.

---

## 8. Scaling intuition

Q/K/V projection cost increases with:

    batch size B
    sequence length S
    hidden dimension D
    projection dimension

For standard MHA:

    cost ∝ B × S × D²

Therefore increasing hidden dimension is especially expensive.

---

## 9. Projection vs reshape

These are different operations.

Projection:

    X
     ↓
    Linear / MatMul
     ↓
    Q

This performs substantial arithmetic.

Reshape:

    [B,S,D]
       ↓
    [B,S,H,d]

primarily changes how the tensor is viewed/interpreted.

Do not treat every tensor operation in a Transformer as having the same
compute cost.

---

## 10. Separate Q/K/V projections vs combined QKV

Mathematically:

    Q = XWQ
    K = XWK
    V = XWV

can be implemented using one combined projection:

    WQKV = [WQ | WK | WV]

    QKV = XWQKV

followed by splitting:

    QKV
     ↓
    ┌───┬───┬───┐
    Q   K   V

This can reduce overhead and allow more efficient hardware utilization.

The exact implementation depends on the framework/runtime.

---

## 11. Model → framework → runtime → hardware

At the model level:

    Q = XWQ

At the framework level:

    nn.Linear

At the tensor/operator level:

    MatMul / Gemm-like computation

At runtime/compiler level:

    lower/map the operation to target-supported implementation

At hardware level:

    execute using matrix/tensor compute resources

Conceptual pipeline:

    HF/PyTorch
        ↓
    Linear
        ↓
    MatMul/Gemm
        ↓
    Runtime/compiler
        ↓
    NPU implementation/kernel
        ↓
    NPU hardware

---

## 12. Memory perspective

Q/K/V projection requires:

    Read input activations X
    Read projection weights
    Perform matrix computation
    Write Q/K/V outputs

Therefore performance is not determined by FLOPs alone.

Actual performance depends on:

- matrix dimensions
- dtype
- memory hierarchy
- weight reuse
- batching
- kernel efficiency
- hardware compute capability
- runtime/compiler optimizations

---

## 13. Embedding vs Q/K/V

### Embedding

    token ID
        ↓
    lookup
        ↓
    vector

Characteristics:

- very little arithmetic
- memory access important
- low arithmetic intensity

### Q/K/V

    hidden states
        ↓
    matrix multiplication
        ↓
    Q/K/V

Characteristics:

- substantial arithmetic
- matrix compute
- memory still matters
- hardware matrix/tensor units can be important

---

## 14. MHA vs GQA/MQA preview

Standard MHA:

    Q heads = H
    K heads = H
    V heads = H

GQA:

    Q heads = H
    K heads = fewer
    V heads = fewer

Therefore GQA can reduce:

- K/V projection dimensions
- K/V parameter sizes
- K/V runtime activation sizes
- KV-cache size

This is an example of a model architecture decision producing
systems-level consequences.

---

## 15. Why don't we normally cache Q?

During autoregressive decoding:

- Q is needed for the current token.
- Previous K and V are needed by future tokens.

Therefore:

    K → cached
    V → cached

while Q is generally computed for the current decoding step.

This will be studied deeply in the KV Cache module.

---

## 16. How to reason about real code

When seeing:

    q = self.q_proj(hidden_states)
    k = self.k_proj(hidden_states)
    v = self.v_proj(hidden_states)

ask:

1. What is the input shape?
2. What are the Q/K/V output shapes?
3. What are the projection weight shapes?
4. How many parameters are involved?
5. What matrix multiplications occur?
6. How many FLOPs approximately?
7. How much data must be read/written?
8. Are Q/K/V projected separately or together?
9. How are tensors reshaped into heads?
10. What runtime operators represent the computation?
11. What implementation/kernel executes it?
12. How does the NPU execute the matrix computation?
13. What could become the bottleneck?

---

## 17. Core mental model

    Hidden states X
          │
          ├───────────────┐
          │               │
          ▼               ▼
       WQ/WK/WV       model parameters
          │
          ▼
        Q, K, V
          │
          ▼
    reshape into heads
          │
          ▼
      Attention

Underneath:

    MODEL
    Q = XWQ, K = XWK, V = XWV
          ↓
    COMPUTE
    large matrix multiplications
          ↓
    MEMORY
    weights + activations read/written
          ↓
    RUNTIME
    Linear → MatMul/Gemm-like operation
          ↓
    KERNEL
    optimized matrix multiplication
          ↓
    NPU
    matrix/tensor compute hardware

---

## 18. Core takeaway

Q/K/V projections transform the same hidden representation into three
different representations required by attention.

Unlike embedding lookup, Q/K/V projections are large matrix
multiplications and therefore represent a substantial computational
workload during Transformer inference.

The important systems perspective is:

    Model concept
        ↓
    Linear projection
        ↓
    Matrix multiplication
        ↓
    Runtime/compiler lowering
        ↓
    Hardware kernel
        ↓
    NPU execution

The goal is not merely to know that Q/K/V exist, but to understand
what they cost and how that cost travels through the ML execution stack.
