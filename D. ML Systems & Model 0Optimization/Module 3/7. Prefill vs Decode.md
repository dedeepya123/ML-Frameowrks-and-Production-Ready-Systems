# Module 3 — Lesson 7
# Prefill vs Decode

## Autoregressive Inference

LLM generation has two fundamentally different phases:

1. Prefill
2. Decode

---

## Prefill

Prefill processes the input prompt.

Example:

Prompt length = S

Input tensor:

[B, S, D]

Many sequence positions can be processed in parallel.

Characteristics:

- large GEMMs
- high parallelism
- high weight reuse
- usually higher arithmetic intensity
- generally better accelerator utilization
- attention interaction has O(S²) complexity

During prefill, K and V are computed for all prompt tokens and stored in the KV cache.

---

## Decode

Decode generates new tokens autoregressively.

For one new token:

Input:

[B, 1, D]

The Transformer still runs for every layer.

However, previous K/V values do not need to be recomputed.

They are read from the KV cache.

Characteristics:

- one/few new tokens per step
- smaller GEMMs
- lower weight reuse
- often lower arithmetic intensity
- more memory-bandwidth sensitivity
- KV cache reads become important
- attention cost grows with current context length

---

## KV Cache

During prefill:

K/V for prompt tokens are computed and stored.

During decode:

new K/V are computed for the new token and appended to the cache.

The query for the new token attends to:

K_cache and V_cache containing previous tokens.

This avoids recomputing K/V for all previous tokens.

---

## Attention Scaling

Prefill:

Q = [B,H,S,Dh]
K = [B,H,S,Dh]

QKᵀ produces:

[B,H,S,S]

Attention interaction:

O(S²D)

Decode:

Q_new = [B,H,1,Dh]

K_cache = [B,H,L,Dh]

Q_new K_cacheᵀ produces:

[B,H,1,L]

Attention per new token:

O(LD)

where L is current context length.

Therefore:

Prefill attention:
O(S²D)

Decode attention per token:
O(LD)

---

## MLP Scaling

Prefill:

[B,S,D] × [D,Dff]

Compute:

O(SDDff)

Decode:

[B,1,D] × [D,Dff]

Compute:

O(DDff) per new token

The same model weights are reused, but decode has far fewer input tokens per step.

---

## Arithmetic Intensity Connection

Prefill:

many tokens use the same weights

→ high weight reuse

→ higher arithmetic intensity

→ better compute utilization

Decode:

few tokens use the same large weights

→ lower weight reuse

→ lower arithmetic intensity

→ memory bandwidth becomes more important

This is a major reason decode can be memory-sensitive.

---

## Weight + KV Cache Memory

Decode has two major memory consumers:

1. Model weights
2. KV cache

Model weights must repeatedly participate in the computation.

KV cache must be read to perform attention against previous tokens.

As context length grows:

KV cache size ↑
KV cache reads ↑
attention work ↑

---

## Batching

Decode with B sequences gives:

[B,D] × [D,Dff]

instead of:

[1,D] × [D,Dff]

Larger batches provide more weight reuse and can improve hardware utilization.

However:

batch size ↑
→ KV cache memory ↑

Therefore batching creates a tradeoff between:

- throughput
- latency
- memory
- hardware utilization

---

## Production Metrics

TTFT (Time To First Token):

request → prefill → first generated token

Therefore TTFT is strongly influenced by prefill performance.

Inter-token latency:

time between generated tokens during decode.

Therefore token generation speed is strongly influenced by decode performance.

---

## Systems Mental Model

Prefill:

Prompt
→ large parallel computation
→ KV cache creation
→ first token

Decode:

New token
→ small GEMMs
→ read KV cache
→ LM head
→ next token
→ repeat

---

## Key Insight

Prefill and decode are not simply two names for the same computation.

They have fundamentally different performance characteristics.

Prefill is usually more compute-oriented because it processes many tokens together.

Decode is often more memory-oriented because it processes few new tokens while repeatedly accessing model weights and the growing KV cache.

Always analyze them separately when reasoning about inference performance.
