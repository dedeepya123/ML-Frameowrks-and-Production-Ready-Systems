# Module 1 — The Inference System

## Lesson 1 — From Model to Hardware

### Core idea

Calling:

model(input)

does not mean Python performs the actual numerical computation.

The computation passes through multiple layers:

Model
→ Framework
→ Operator
→ Runtime / Backend
→ Kernel
→ Hardware

---

## 1. Model

Example:

GemmaForCausalLM
→ GemmaModel
→ DecoderLayer
→ Attention / MLP

The model describes the computation.

---

## 2. Operator

An operator represents a mathematical/computational operation.

Examples:

- matmul
- addition
- softmax
- layer normalization
- convolution

Example:

Y = XW

PyTorch may expose this through:

torch.matmul()
nn.Linear()

---

## 3. Runtime / Backend

The runtime/backend determines how the operator should execute on a particular device.

Same model/operator can execute differently on:

- CPU
- GPU
- NPU

---

## 4. Kernel

A kernel is a lower-level implementation that performs an operation on the target hardware.

Conceptually:

PyTorch operator
→ backend
→ kernel
→ hardware

---

## 5. Hardware

Actual computation happens using hardware resources.

Examples:

- CPU cores
- GPU compute units
- NPU compute units
- caches
- memory
- memory bandwidth

---

## 6. Model ≠ Execution

A model architecture describes what should be computed.

The runtime/hardware determines how that computation is executed.

Therefore the same model can have very different performance on different hardware.

---

## 7. First systems principle

Number of operations != execution time.

Performance depends on factors such as:

- computation
- memory movement
- memory bandwidth
- communication
- synchronization
- hardware utilization

Therefore:

Optimize the bottleneck, not merely the largest-looking component.

---

## 8. Two questions to ask for every operation

1. How much computation is required?

2. How much data must move?

These lead to the concepts:

- FLOPs
- memory footprint
- memory bandwidth
- compute-bound
- memory-bound
- arithmetic intensity

---

## 9. Transformer example

Attention at model level:

Q/K/V
→ RoPE
→ attention
→ output projection

At execution level this becomes multiple operators/kernels.

Therefore:

Model component
!=
single hardware operation

---

## 10. Execution graph

Example:

x
→ Linear
→ ReLU
→ Linear
→ output

This forms an execution graph.

A runtime/compiler can analyze this graph for optimizations such as:

- operator fusion
- kernel fusion
- memory optimization
- graph transformations

---

## 11. Code-reading questions

When reading production ML code ask:

### Model
What mathematical operation is this?

### Tensor
What are the shapes and dtypes?

### Compute
How much computation is required?

### Memory
How much data is read/written?

### Runtime
Which backend executes it?

### Hardware
Where does it actually execute?

### Performance
What could make it slow?

---

## Core mental model

MODEL
"What computation do I want?"

↓  

OPERATOR
"What mathematical operation is this?"

↓

RUNTIME
"How should this execute on this device?"

↓

KERNEL
"What low-level implementation performs it?"

↓

HARDWARE
"What physical resources execute it?"

---

## Key takeaway

Previously we learned to trace:

generate()
→ forward()
→ model
→ layer
→ attention

Now we extend the trace:

generate()
→ forward()
→ model component
→ operator
→ runtime/backend
→ kernel
→ hardware

This is the foundation of ML Systems reasoning.
