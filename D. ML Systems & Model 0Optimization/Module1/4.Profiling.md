# Module 1 — The Inference System

## Lesson 4 — Profiling: Finding the Bottleneck

## 1. Profiling

Profiling is the process of measuring execution to understand where time/resources are being spent.

Core question:

Where is the time going?

---

## 2. Start with a baseline

Measure the complete workload first.

Example:

Total inference latency = 420 ms

This establishes a baseline.

---

## 3. Warmup

Initial executions may include:

- initialization
- memory allocation
- compilation
- kernel setup
- cache initialization

Therefore use:

Warmup
→ Warmup
→ ...
→ Measure steady state

---

## 4. Profiling hierarchy

Go deeper only when necessary:

End-to-end
→ Model / Layer
→ Operator
→ Kernel
→ Hardware behavior

---

## 5. Layer-level profiling

Example:

Embedding = 2 ms
Attention = 25 ms
MLP = 60 ms
Other = 13 ms

MLP is a likely hotspot.

---

## 6. Operator-level profiling

Inside MLP:

Gate projection = 15 ms
Up projection = 15 ms
Activation = 2 ms
Down projection = 28 ms

Down projection becomes the next investigation target.

---

## 7. Kernel-level profiling

An operator may execute through:

- one kernel
- multiple kernels
- fused kernels

Profiling can reveal actual kernel execution.

---

## 8. Hardware-level profiling

A kernel can be investigated through:

- compute utilization
- memory bandwidth
- cache behavior
- synchronization
- memory transfers
- occupancy
- hardware utilization

Goal:

Understand WHY the kernel is slow.

---

## 9. Profiling vs benchmarking

Profiling asks:

Where is time going?

Benchmarking asks:

How fast is the complete system?

Use profiling to find bottlenecks.

Use controlled benchmarking to measure the final improvement.

---

## 10. Instrumentation

Basic timing/instrumentation measures specific regions of code.

Example:

start timer
→ operation
→ end timer

Useful for simple measurements.

---

## 11. Trace

A trace shows execution over time.

Conceptually:

CPU:
prepare → wait → prepare

GPU:
kernel A → kernel B → kernel C

Memory:
transfer → transfer

Traces help identify:

- idle periods
- synchronization
- kernel launch overhead
- CPU/GPU interaction
- memory transfers

---

## 12. Amdahl's Law intuition

If a component represents a fraction of total runtime, that fraction limits the maximum possible end-to-end speedup.

Example:

Total = 100 ms

Component A = 90 ms
Everything else = 10 ms

Even if A becomes infinitely fast:

New total = 10 ms

Maximum speedup = 10x.

Therefore:

Optimizing a small component cannot produce a large end-to-end speedup.

---

## 13. Local speedup != end-to-end speedup

Example:

Attention:

30 ms → 15 ms

Total:

100 ms → 85 ms

Attention became 2x faster, but the entire model only became:

100 / 85 ≈ 1.18x faster.

Always measure end-to-end performance.

---

## 14. Profiling overhead

Profiling can change execution behavior and timing.

Therefore:

Profiler measurements
!=
always exact production latency.

Use profiling to understand behavior.

Use controlled benchmarks for final performance comparisons.

---

## 15. Optimization workflow

1. Define workload
2. Establish baseline
3. Profile
4. Identify bottleneck
5. Form hypothesis
6. Optimize
7. Benchmark
8. Validate correctness

---

## 16. Example ML systems workflow

Goal:

Make Gemma inference faster on an accelerator.

Define:

- model
- prompt length
- output length
- batch size
- dtype
- target hardware

Measure:

- TTFT
- decode tokens/sec
- memory
- power if relevant

Profile:

- operators
- kernels
- memory movement
- synchronization
- transfers
- unsupported operations

Then optimize the actual bottleneck.

---

## 17. Core mental model

Do NOT think:

"Model is slow → try quantization."

Think:

Model is slow
→ measure
→ profile
→ find bottleneck
→ understand why
→ choose optimization
→ measure again

---

## Key takeaway

The most important optimization skill is not knowing many optimization techniques.

It is knowing how to answer:

"Where is the time going, and why?"

Profile first.
Optimize second.
Benchmark third.
