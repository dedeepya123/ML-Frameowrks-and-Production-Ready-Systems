# Module 1 — The Inference System

## Lesson 5 — The Optimization Mindset

## 1. Core principle

Never optimize based only on intuition.

Correct workflow:

Define workload
→ Benchmark baseline
→ Profile
→ Find bottleneck
→ Understand why
→ Form hypothesis
→ Optimize
→ Benchmark
→ Validate correctness
→ Check regressions
→ Repeat

---

## 2. Define workload

Always specify:

- model
- hardware
- dtype
- batch size
- prompt length
- output length
- prefill/decode/end-to-end
- relevant performance metric

Performance numbers are meaningful only in context.

---

## 3. Baseline

Measure the original implementation.

Example:

TTFT = 420 ms
Decode = 32 tokens/sec
Memory = 2.8 GB

These become the baseline.

---

## 4. Profile

Find where time/resources are being spent.

Example:

Attention = 28%
MLP = 51%
Other = 21%

Then investigate the largest meaningful hotspot.

---

## 5. Understand the bottleneck

Do not stop at:

"MLP is slow."

Go deeper:

MLP
→ Down projection
→ MatMul
→ Kernel
→ memory/computation behavior

Goal:

Understand WHY it is slow.

---

## 6. Hypothesis

A good optimization starts with a testable hypothesis.

Bad:

"Let's optimize this."

Good:

"The kernel appears memory-bound, so reducing memory traffic should reduce latency."

---

## 7. Choose optimization based on bottleneck

Possible mappings:

Memory bottleneck
→ reduce memory movement
→ improve locality
→ change layout
→ fusion
→ quantization

Compute bottleneck
→ better kernel
→ lower precision
→ hardware-specific implementation
→ better parallelism

Launch overhead
→ fusion
→ fewer kernels
→ batching

Poor utilization
→ increase parallelism
→ improve shapes
→ batching

CPU/accelerator transfers
→ keep tensors on device
→ reduce synchronization
→ change execution flow

These are examples, not universal rules.

---

## 8. Local speedup != end-to-end speedup

If an operation is 50% of total runtime and becomes infinitely fast:

Maximum possible overall speedup = 2x.

Example:

100 ms total
50 ms hotspot

Hotspot:
50 → 0 ms

New total:
50 ms

Maximum:
2x

---

## 9. Bottleneck migration

After optimizing one bottleneck, another often becomes dominant.

Example:

MLP
→ optimize
→ Attention becomes bottleneck
→ optimize
→ Memory becomes bottleneck

Optimization is iterative.

---

## 10. Correctness

Performance optimization must preserve acceptable model behavior.

Validation may include:

- numerical comparison
- tolerance checks
- output comparison
- accuracy
- perplexity
- task metrics
- generation behavior

depending on the optimization.

---

## 11. Regression checking

An optimization can improve one metric while hurting another.

Example:

TTFT:
420 → 350 ms

Decode:
32 → 25 tok/s

Therefore always check the relevant metrics together.

---

## 12. Controlled benchmarking

Compare the same workload:

same model
same hardware
same dtype
same batch
same prompt length
same output length
same warmup
same measurement procedure

Otherwise the comparison may be invalid.

---

## 13. Optimization as an experiment

Hypothesis
→ change
→ measure
→ compare
→ conclude

Example:

Hypothesis:
Memory movement limits decode.

Change:
Reduce memory traffic.

Expected:
Memory traffic ↓
Decode latency ↓

Measure and determine whether the hypothesis was supported.

---

## 14. Real ML Systems workflow

Goal:
Optimize Gemma on target accelerator.

1. Define workload
2. Establish baseline
3. Profile
4. Identify hotspot
5. Understand tensor operations
6. Understand kernel/runtime behavior
7. Form hypothesis
8. Modify implementation
9. Benchmark
10. Validate correctness
11. Check regressions
12. Repeat

---

## 15. Core mental model

Model
→ Operators
→ Runtime
→ Kernels
→ Memory + Compute
→ Hardware
→ Performance

Performance problem
→ Measure
→ Profile
→ Understand
→ Optimize
→ Validate

---

## Key takeaway

The most valuable optimization skill is not memorizing optimization techniques.

It is being able to answer:

1. What is slow?
2. Why is it slow?
3. What evidence proves it?
4. What change should address the bottleneck?
5. Did the change actually improve end-to-end performance?
6. Did correctness remain intact?
7. Did another metric regress?

That is the foundation of ML Systems performance engineering.
