# Module 2 — Compute vs Memory

## Lesson 2 — Roofline Model

## 1. Purpose

Roofline Model helps reason about whether an operation is limited by:

- compute
- memory bandwidth

It connects:

FLOPs
+
Bytes moved
+
Hardware limits

---

## 2. Arithmetic Intensity

AI = FLOPs / Bytes moved

Low AI:
little computation per byte

High AI:
lots of computation per byte

---

## 3. Hardware limits

Suppose:

Peak compute = 100 TFLOP/s
Memory bandwidth = 1 TB/s

Machine balance / ridge point:

AI_critical =
Peak Compute / Memory Bandwidth

= 100 / 1

= 100 FLOPs/byte

Therefore:

AI < 100 FLOPs/byte
→ memory-bound region

AI > 100 FLOPs/byte
→ compute-bound region

---

## 4. Roofline equation

Achievable performance is bounded by:

P <= min(
    Peak Compute,
    Memory Bandwidth × Arithmetic Intensity
)

The lower roof is the limiting factor.

---

## 5. Example

Hardware:

Peak compute = 100 TFLOP/s
Bandwidth = 1 TB/s

Operation:

AI = 10 FLOPs/byte

Memory roof:

1 × 10 = 10 TFLOP/s

Therefore:

P <= min(100, 10)
P <= 10 TFLOP/s

→ memory-bound.

---

## 6. Compute-bound example

AI = 200 FLOPs/byte

Memory roof:

1 × 200 = 200 TFLOP/s

Peak compute = 100 TFLOP/s

Therefore:

P <= min(100, 200)
P <= 100 TFLOP/s

→ compute-bound.

---

## 7. Optimization implication

Memory-bound:

Focus on:

- reducing memory traffic
- fusion
- better tensor layout
- data reuse
- locality
- lower precision
- avoiding unnecessary copies

Compute-bound:

Focus on:

- kernel efficiency
- tiling
- parallelism
- hardware matrix units
- lower precision
- instruction utilization

---

## 8. Transformer examples

Large GEMM:

- many FLOPs
- significant data reuse
- often high arithmetic intensity
- can be compute-bound

RMSNorm:

- relatively few FLOPs
- reads/writes substantial data
- often lower arithmetic intensity
- can be memory-sensitive

Elementwise operations:

- very few FLOPs
- significant memory movement
- often memory-sensitive

---

## 9. Fusion

Separate:

RMSNorm
→ write
→ Activation
→ write
→ Scale
→ write

causes repeated memory movement.

Fused:

read
→ RMSNorm
→ Activation
→ Scale
→ write

can reduce memory traffic substantially.

FLOPs may not change much.

The speedup comes primarily from reducing data movement.

---

## 10. Prefill vs Decode

Prefill:

- larger workloads
- more parallelism
- larger matrix operations
- can be compute-heavy

Decode:

- usually one/few new tokens
- smaller/skinny operations
- KV-cache access becomes important
- memory behavior can dominate

Therefore the same operation/model can have different bottlenecks in prefill and decode.

---

## 11. Algorithm vs hardware

Algorithmic complexity:

Example:
Attention = O(T²D)

Operation count:

Example:
≈ 2T²D FLOPs

Hardware behavior:

- bandwidth
- cache
- kernel efficiency
- parallelism
- utilization
- memory layout

These are different levels of analysis.

---

## 12. Roofline is an upper-bound model

Peak hardware numbers are theoretical.

Real kernels may achieve less because of:

- inefficient shapes
- insufficient parallelism
- memory access problems
- synchronization
- launch overhead
- instruction limitations

Roofline helps establish the likely limiting resource, but profiling is still required.

---

## 13. Core workflow

Slow operation
→ measure
→ estimate FLOPs
→ estimate bytes moved
→ calculate arithmetic intensity
→ compare against hardware ridge point
→ determine likely compute/memory limitation
→ inspect kernel
→ optimize accordingly
→ benchmark again

---

## Key takeaway

FLOPs alone are insufficient.

The important relationship is:

Arithmetic Intensity = FLOPs / Bytes

and:

Achievable Performance <=
min(Peak Compute,
    Bandwidth × Arithmetic Intensity)

Roofline gives a mental model for understanding:

"Is this operation limited by computation or by moving data?"
