# Module 2 — Compute vs Memory

## Lesson 3 — Memory Hierarchy & Data Movement

## 1. Memory is hierarchical

Conceptually:

Registers
→ Local/Shared memory
→ Cache
→ Device memory
→ System memory

Exact hierarchy depends on hardware.

General principle:

Faster memory
→ smaller
→ closer to compute

Slower memory
→ larger
→ farther from compute

---

## 2. Registers

Registers are tiny, very fast storage locations close to the execution units.

They are useful for keeping values that are actively being computed.

They are extremely limited.

---

## 3. Local / shared memory

Accelerators may provide fast on-chip memory such as:

- shared memory
- SRAM
- scratchpad/local memory

Keeping data close to compute can reduce expensive external memory accesses.

---

## 4. Cache

Cache keeps recently/frequently used data closer to compute.

Cache hit:
data found in a faster memory level.

Cache miss:
data must be fetched from a lower/slower level.

---

## 5. Data reuse

Bad:

load value from slow memory
→ use once
→ reload
→ use again
→ reload

Better:

load once
→ keep locally
→ reuse many times

Data reuse reduces memory traffic and can increase arithmetic intensity.

---

## 6. Locality

### Temporal locality

Recently used data may be used again soon.

Example:

x
x
x
x

### Spatial locality

Nearby memory locations may be accessed together.

Example:

x[0]
x[1]
x[2]
x[3]

Good locality generally makes memory access more efficient.

---

## 7. Tensor layout

Tensor shape:

Describes mathematical dimensions.

Tensor layout:

Describes how values are physically organized in memory.

Same mathematical tensor can have different layouts.

Layout strongly affects kernel efficiency.

---

## 8. View vs copy

A reshape/transpose may sometimes only change how memory is interpreted.

Other transformations may require an actual data copy/rearrangement.

Copy/rearrangement means:

old memory
→ move/rearrange
→ new memory

This consumes:

- bandwidth
- time
- memory

Therefore production code must be analyzed for physical data movement, not just mathematical operations.

---

## 9. Matrix multiplication and tiling

Efficient GEMM kernels divide matrices into tiles.

Instead of repeatedly loading the same values from slow memory:

load tile
→ place in fast local storage
→ reuse tile
→ perform many operations

This increases data reuse and arithmetic intensity.

---

## 10. Fusion

Separate:

A
→ write
→ B
→ write
→ C
→ write

can cause repeated memory movement.

Fusion can perform:

read
→ A
→ B
→ C
→ write

while keeping intermediate values closer to compute.

Main benefit can be reduced memory traffic.

Fusion is not always better because it can increase:

- register usage
- local memory usage
- kernel complexity

---

## 11. Memory bandwidth vs latency

Latency:

Time for an individual memory access.

Bandwidth:

Amount of data that can be transferred per second.

They are different concepts.

---

## 12. Parallelism can hide latency

If many operations are available:

memory request A
memory request B
memory request C
→ compute other work while waiting

This can hide memory latency.

Irregular memory accesses can make this harder.

---

## 13. KV cache

During decode:

Q
+
cached K
+
cached V

The efficiency of attention depends not only on FLOPs but also on:

- KV-cache layout
- memory access pattern
- locality
- bandwidth
- reuse

Therefore KV-cache layout is a systems/performance concern.

---

## 14. Scatter

Scatter-like operations may involve writing to non-contiguous locations.

Important questions:

- Where are values written?
- Are writes contiguous?
- How much data moves?
- What kernel executes it?
- Why does the runtime require this layout?

Mathematically correct does not automatically mean memory-efficient.

---

## 15. Transformer examples

RMSNorm:

few FLOPs + tensor read/write
→ often memory-sensitive

QKV projection:

large GEMM + data reuse
→ often compute-heavy

RoPE:

elementwise operation + tensor movement
→ often memory-sensitive

Residual:

read X
+ read F(X)
+ add
+ write Y

Very little arithmetic but non-trivial memory movement.

Decode attention:

read Q
+ read KV cache
+ attention computation

KV-cache access pattern becomes important.

---

## 16. Important chain

Tensor layout
→ memory access pattern
→ locality/reuse
→ memory traffic
→ arithmetic intensity
→ roofline position
→ performance

---

## 17. Two-layer thinking

For every tensor operation ask:

### Mathematical layer

What does it compute?

### Physical layer

Where are inputs?

How are they laid out?

Where is output written?

How many bytes move?

Can data be reused?

Which memory level is involved?

Which kernel executes it?

---

## Key takeaway

Tensor operations are not just mathematical operations.

A production ML system must also decide:

How data is laid out
→ where it is stored
→ how it is moved
→ how often it is reused
→ how efficiently the hardware can access it

The goal is often:

Do more useful computation
while moving less data
and keeping frequently used data close to compute.
