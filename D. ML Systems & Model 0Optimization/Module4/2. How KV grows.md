# Module 4 — Lesson 2: How KV Cache Grows

## Core idea

Each generated token adds one new K and one new V for every layer and KV head.

KV cache grows linearly with sequence length.

## Memory added per token

KV_per_token =
2 × B × N × Hkv × Dh × dtype_bytes

2 = K + V

## Total cache

KV_total =
KV_per_token × L

Therefore:

KV_total ∝ B × L × N × Hkv × Dh × dtype

## Context growth

Final context:

L_final = prompt_tokens + generated_tokens

Both prompt tokens and generated tokens occupy KV cache.

## Batch

B ↑
→ KV memory ↑ linearly

Therefore concurrency directly consumes KV memory.

## Variable-length requests

Different requests can have different context lengths.

This creates a runtime memory-management problem.

Production runtimes avoid reallocating the entire cache every token and may use:

- preallocation
- chunked allocation
- block/paged allocation

## Logical vs Physical Cache

Logical:
tokens 1...L

Physical:
KV may be stored across blocks/pages in different memory locations.

The runtime maintains the mapping.

This idea leads to Paged Attention / KV cache management.

## Systems Insight

KV cache is persistent per-request state.

It affects:

- memory capacity
- maximum context
- concurrency
- serving throughput

But cache capacity and cache bandwidth are different questions.

Capacity:
How much KV memory is stored?

Bandwidth:
How much KV data must be read during decode?
