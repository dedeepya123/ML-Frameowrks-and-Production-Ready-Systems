# Module 4 — Lesson 3: Memory Bandwidth During Decode

## Core Idea

During decode, attention must access previous K/V from the KV cache.

Therefore KV cache is not only a memory-capacity problem.
It can also become a memory-bandwidth bottleneck.

## Simplified KV Traffic

For one sequence at context length L:

K + V elements:

2 × L × Hkv × Dh

Bytes:

2 × L × Hkv × Dh × dtype_bytes

Across B sequences and N layers:

KV traffic is approximately:

2 × B × N × L × Hkv × Dh × dtype_bytes

per decode step, as a simplified upper-level model.

Actual hardware traffic depends on caching, tiling,
memory hierarchy, kernel implementation, etc.

## Memory-Bound Reasoning

For memory-sensitive work:

Time ≈ Bytes moved / Memory Bandwidth

Arithmetic Intensity:

AI = FLOPs / Bytes

Decode often has lower arithmetic intensity because:

- few new tokens are processed
- model weights are large
- KV cache must be accessed
- useful FLOPs are relatively small compared with data movement

Therefore decode can become memory-bandwidth sensitive.

## Context Length

L ↑
→ KV capacity ↑
→ KV data accessed per decode step ↑

Therefore long context affects both:

1. memory capacity
2. memory bandwidth

## GQA / MQA

Hkv ↓
→ KV cache size ↓
→ KV traffic ↓

This can improve both memory capacity and bandwidth pressure.

## Batch Tradeoff

Batch ↑

Benefits:
- more weight reuse
- better compute utilization
- potentially better throughput

Costs:
- KV memory ↑
- KV traffic ↑

Therefore maximum batch size is not automatically optimal.

## Important Distinction

KV capacity:
"Can the cache fit?"

KV bandwidth:
"Can the hardware move/access the cache fast enough?"

## Systems Reasoning

If decode has low NPU utilization, don't immediately conclude
the compute kernels are inefficient.

Ask:

- Is memory bandwidth saturated?
- What is arithmetic intensity?
- How many bytes are moved?
- How large are the kernels?
- How much KV data is accessed?
- Is the memory layout efficient?
