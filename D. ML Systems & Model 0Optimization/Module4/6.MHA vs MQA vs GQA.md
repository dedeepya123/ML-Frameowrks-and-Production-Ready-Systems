# Module 4 — Lesson 6: MHA vs MQA vs GQA

## MHA

Q heads = K heads = V heads

Example:
Q=32, K=32, V=32

## GQA

More Q heads than KV heads.

Example:
Q=32, K=8, V=8

Groups of query heads share K/V heads.

## MQA

Single KV head.

Example:
Q=32, K=1, V=1

## Important

MHA/GQA/MQA are attention architecture choices,
not simply runtime inference flags.

Changing MHA → GQA changes K/V projection shapes
and model parameterization.

## Systems Benefit

KV memory:

KV ∝ Hkv

Therefore:

fewer KV heads
→ smaller KV cache
→ less KV traffic
→ potentially better decode efficiency.

## Cache Abstraction

HF conceptually manages K/V state per Transformer layer:

Layer 0 → K/V
Layer 1 → K/V
...
Layer N → K/V

But the HF cache object is a logical/framework abstraction.

It does NOT necessarily represent the physical accelerator memory layout.

## Logical vs Physical Cache

Dynamic logical cache:
cache length grows as tokens arrive.

Physical implementation may still use:
- preallocated buffers
- blocks
- pages
- other runtime-managed allocations

Therefore:

dynamic logical state ≠ dynamic physical allocation

## Architecture vs Runtime

Model architecture:
MHA/GQA/MQA
↓
determines K/V shapes

Runtime:
allocation, layout, addressing, buffer management

Hardware:
actual memory hierarchy and execution

## Important Distinction

GQA/MQA:
sharing K/V across query heads → architecture

KV buffer sharing/prefix sharing/paging:
runtime/serving concepts

Do not confuse them.

Q: Are MQA/GQA just inference-time optimizations?

No. They are fundamentally attention architectural choices because they change the number of K/V heads and therefore the model's parameterization and tensor shapes.

Q: Can an MHA model simply switch to GQA at inference?

Not as a normal runtime switch. You need a model whose attention architecture supports GQA, or an explicit model-conversion/adaptation procedure with appropriate quality validation.

Q: Does HF manage KV per Transformer layer?

Yes, conceptually. Each layer has its own K/V state, and the cache abstraction manages that state during generation.

Q: Does the HF cache object equal the physical accelerator cache?

No. It is a model/framework-level representation. The runtime/compiler can transform how that state is represented and allocated on the accelerator.

Q: Can a dynamic cache still use preallocated physical memory?

Yes. Logical dynamic growth and physical dynamic allocation are separate concepts.

Q: Does the physical KV-cache implementation depend on the accelerator/runtime?

Yes. The model specifies the required logical state; the runtime/hardware stack determines how that state is actually stored and accessed
